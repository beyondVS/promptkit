## User Scenarios & Testing *(mandatory)*

### User Story 1 - 개별 배포 단위 독립 검증 (Priority: P1)

패키지 유지보수자는 모노레포의 각 배포 단위를 깨끗한 격리 환경에서 개별적으로 준비하고, 다른 저장소 구성 요소에 기대지 않고 설치 및 기본 사용이 가능한지 확인한다.

**Why this priority**: 독립 배포 가능성은 모노레포 외부의 사용자가 필요한 패키지만 선택할 수 있게 하는 핵심 계약이며, 숨은 경로 참조나 미선언 의존성을 가장 먼저 차단한다.

**Independent Test**: 각 배포 단위를 하나씩 새 배포 산출물과 Git 서브디렉터리 직접 설치 경로로 각각 깨끗한 환경에 설치한 뒤, 공개 진입점을 불러오고 대표적인 최소 동작을 수행하여 저장소 루트나 관계없는 패키지 없이도 사용할 수 있음을 확인한다.

**Acceptance Scenarios**:

1. **Given** 저장소 소스나 기존 설치 패키지가 노출되지 않은 깨끗한 환경, **When** 코어 SDK 배포 단위만 설치하고 공개 진입점을 사용하면, **Then** 설치와 최소 조회·컴파일 동작이 성공하고 서버 및 Django 통합 코드는 필요하지 않다.
2. **Given** 동일한 조건의 별도 깨끗한 환경, **When** Django 통합 배포 단위를 선언된 의존성과 함께 설치하고 공개 진입점을 사용하면, **Then** 설치와 최소 초기화가 성공하고 서버 애플리케이션 소스는 필요하지 않다.
3. **Given** 동일한 조건의 별도 깨끗한 환경, **When** Prompt Server 배포 단위를 설치하고 기본 상태 검증을 수행하면, **Then** 서버가 요구하는 구성 요소만으로 검증이 성공하고 통합 패키지의 비공개 소스에 의존하지 않는다.

### User Story 2 - 패키지 조합 상호 운용 검증 (Priority: P2)

통합 패키지 사용자는 코어 SDK와 Django 통합 패키지를 하나의 깨끗한 호스트 환경에 함께 설치하여, 호환되는 공개 계약을 통해 정상적으로 연동되는지 확인한다.

**Why this priority**: 개별 설치 성공만으로는 실제 조합에서 발생할 수 있는 버전 충돌, 모듈 가림, 중복 등록 또는 설정 충돌을 발견할 수 없다.

**Independent Test**: 코어 SDK와 Django 통합 패키지의 배포 산출물을 같은 격리 환경에 설치하고 최소 호스트 애플리케이션을 초기화한 뒤, 통합 계층을 통해 등록된 SDK가 프롬프트 조회 및 클라이언트 측 컴파일 계약을 유지하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 호환 대상으로 선언된 코어 SDK와 Django 통합 패키지 산출물, **When** 두 산출물을 깨끗한 환경에 함께 설치하고 최소 호스트 애플리케이션을 초기화하면, **Then** 의존성 충돌이나 중복 모듈 없이 단일 SDK 인스턴스를 사용할 수 있다.
2. **Given** 정상 초기화된 조합 환경, **When** 통합 계층을 통해 프롬프트 조회 결과를 받아 변수를 적용하면, **Then** 공개 결과 형식과 클라이언트 측 컴파일 동작이 코어 SDK 단독 사용과 동일하다.
3. **Given** 현재 저장소에서 생성한 코어 SDK와 Django 통합 패키지 산출물, **When** 조합 검증을 시작하면, **Then** 두 산출물의 선언된 버전 계약이 서로 일치하는지 확인한 뒤 공개 동작을 검증한다.

### User Story 3 - 재현 가능한 배포 격리 판정 (Priority: P3)

릴리스 담당자는 모든 배포 단위의 산출물과 지원 조합을 한 번의 검증 절차로 확인하고, 실패가 발생하면 영향을 받은 배포 단위와 단계가 명확한 결과를 얻는다.

**Why this priority**: 반복 가능한 전체 판정은 로컬 워크스페이스에서만 우연히 성공하는 상태를 배포 전에 발견하고 릴리스 판단의 근거를 남긴다.

**Independent Test**: 기존 빌드 산출물과 설치 상태를 제거한 출발점에서 전체 격리 검증을 수행하고, 각 배포 단위의 산출물 생성·단독 설치·조합 설치·대표 동작 결과가 개별 항목으로 보고되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이전 산출물과 설치 캐시가 검증 대상에 포함되지 않는 초기 상태, **When** 전체 격리 검증을 수행하면, **Then** 모든 배포 단위가 새 산출물로 평가되고 각 단독 및 조합 시나리오의 통과 여부가 구분된다.
2. **Given** 한 배포 단위에 누락된 런타임 의존성 또는 잘못된 패키지 내용이 있는 상태, **When** 전체 검증을 수행하면, **Then** 해당 배포 단위와 실패 단계가 식별되며 다른 항목의 결과와 혼동되지 않는다.
3. **Given** 모든 지원 시나리오가 통과한 상태, **When** 릴리스 담당자가 결과를 검토하면, **Then** 저장소 내부 경로 주입 없이 독립 배포와 상호 운용이 입증되었음을 한 번에 판정할 수 있다.

### Edge Cases

- 이전에 생성된 산출물이나 설치 캐시가 최신 패키지의 누락 파일 또는 의존성 오류를 가리는 경우
- 같은 이름의 모듈이 저장소 루트와 설치 환경에 동시에 존재하여 설치 산출물 대신 로컬 소스가 불러와지는 경우
- 코어 SDK는 단독 설치에 성공하지만 현재 Django 통합 패키지의 선언된 호환 범위가 현재 코어 SDK 산출물 버전과 맞지 않는 경우
- 패키지 설치 순서에 따라 최종 의존성 집합이나 동작 결과가 달라지는 경우
- 네트워크 또는 외부 서비스가 없어도 가능한 검증과 실제 외부 연결이 필요한 검증이 혼재하는 경우
- 지원하지 않는 런타임 버전에서 설치가 우연히 진행되지만 공개 진입점 사용 시 실패하는 경우

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 검증 절차는 코어 SDK, Django 통합 패키지, Prompt Server를 서로 구분되는 배포 단위로 다루어야 한다.
- **FR-002**: 각 배포 단위는 다른 검증 실행에서 남은 설치 상태와 저장소 내부 import 경로가 없는 깨끗한 환경에서 평가되어야 한다.
- **FR-003**: 각 배포 단위는 해당 단위의 선언된 패키지 소스만으로 새 배포 산출물을 생성할 수 있어야 하며, 새 산출물과 해당 Git 서브디렉터리 직접 설치 경로가 각각 독립 설치에 성공해야 한다.
- **FR-004**: 각 생성 산출물은 선언된 패키지명, 버전, 지원 런타임 범위, 런타임 의존성 및 공개 모듈을 포함해야 한다.
- **FR-005**: 코어 SDK 산출물은 Prompt Server 또는 Django 통합 패키지를 설치하지 않은 환경에서 설치, 공개 import 및 대표 최소 동작을 완료해야 한다.
- **FR-006**: Django 통합 산출물은 선언된 코어 SDK 의존성과 함께 설치되어야 하며 Prompt Server 소스 없이 공개 import 및 최소 호스트 초기화를 완료해야 한다.
- **FR-007**: Prompt Server 산출물은 선언된 런타임 의존성만으로 설치되고 배포 전 기본 상태 검증을 완료해야 한다.
- **FR-008**: 검증 절차는 코어 SDK와 Django 통합 패키지를 함께 설치한 지원 조합에서 공개 객체의 등록, 조회 결과 전달 및 클라이언트 측 컴파일 동작을 확인해야 한다.
- **FR-009**: 조합 검증은 패키지 설치 순서를 바꾸어도 동일한 최종 공개 동작과 호환성 판정을 제공해야 한다.
- **FR-010**: 어떤 검증도 저장소 루트, 편집 가능한 로컬 설치, 미선언 소스 경로 또는 다른 배포 단위의 비공개 파일을 사용해 성공해서는 안 된다.
- **FR-011**: 외부 서비스 연결이 핵심 판정에 필요하지 않은 동작은 대체 가능한 격리 입력으로 검증되어야 하며, 외부 서비스 가용성이 패키징 결함을 가리거나 허위 실패를 만들지 않아야 한다.
- **FR-012**: 전체 검증 결과는 배포 단위별 산출물 생성, 단독 설치, 공개 import, 최소 동작 및 지원 조합 검증을 각각 식별 가능하게 보고해야 한다.
- **FR-013**: 실패 결과는 영향을 받은 배포 단위, 실패 단계 및 재현에 필요한 시나리오를 식별할 수 있어야 한다.
- **FR-014**: 전체 검증은 하나의 배포 단위 실패가 다른 배포 단위의 환경을 오염시키지 않도록 각 시나리오를 격리해야 한다.
- **FR-015**: 버전 상호 운용 검증은 현재 저장소에서 생성한 동일 릴리스의 코어 SDK와 Django 통합 패키지 조합을 대상으로 하며, 두 산출물의 선언된 버전 계약이 일치해야 한다.
- **FR-016**: 검증 범위는 패키지 설치·배포 격리와 공개 계약의 상호 운용에 한정하며, 운영 인프라 배포, 실제 외부 서비스 호출 및 성능 부하 평가는 포함하지 않는다.

### Key Entities

- **배포 단위**: 독립적으로 산출물을 만들고 설치할 수 있는 모노레포 구성 요소로, 패키지명, 버전, 지원 런타임, 의존성 및 공개 진입점 계약을 가진다.
- **배포 산출물**: 특정 배포 단위의 설치 가능한 결과물로, 검증 시 저장소 내부 소스 대신 실제 소비자가 받는 내용을 대표한다.
- **격리 환경**: 이전 설치, 로컬 소스 경로 및 다른 시나리오의 상태를 공유하지 않는 검증 공간이다.
- **호환 조합**: 함께 설치될 수 있다고 선언된 배포 단위와 버전의 집합으로, 기대 공개 동작과 허용 범위를 가진다.
- **검증 결과**: 배포 단위, 시나리오, 단계, 통과 여부 및 실패 식별 정보를 연결하는 릴리스 판정 기록이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 3개 배포 단위 각각이 별도의 깨끗한 환경에서 산출물 생성 후 설치와 Git 서브디렉터리 직접 설치의 두 경로 모두에서 공개 진입점 사용 및 대표 최소 동작을 100% 완료한다.
- **SC-002**: 지원되는 코어 SDK와 Django 통합 패키지 조합은 두 가지 설치 순서 모두에서 동일한 공개 동작을 보이며, 중복 모듈·의존성 충돌·설정 충돌이 0건이다.
- **SC-003**: 전체 검증의 모든 성공 시나리오에서 저장소 루트 또는 다른 배포 단위의 비공개 소스가 사용된 사례가 0건이다.
- **SC-004**: 의도적으로 주입한 누락 의존성과 누락 패키지 내용 실패가 각각 올바른 배포 단위와 단계로 100% 식별된다.
- **SC-005**: 릴리스 담당자는 단일 검증 실행 결과만으로 각 배포 단위의 독립 배포 가능 여부와 지원 조합의 상호 운용 여부를 5분 이내에 판정할 수 있다.
- **SC-006**: 깨끗한 동일 조건에서 전체 검증을 연속 2회 수행했을 때 배포 단위별 판정 결과가 100% 일치한다.

## Assumptions

- 검증 대상 배포 단위는 `promptkit` 코어 SDK, `promptkit-django` 통합 패키지, Prompt Server의 세 가지이며, 모두 독립 설치·배포 검증 대상이다.
- 지원 런타임과 패키지 간 호환 범위는 각 배포 단위가 선언한 메타데이터를 기준으로 하며, 버전 조합 검증은 현재 저장소에서 생성한 동일 릴리스 조합으로 제한한다.
- 핵심 판정은 실제 패키지 소비 환경을 대표하는 새 비편집 설치 산출물과 Git 서브디렉터리 직접 설치 결과를 모두 대상으로 한다.
- 외부 Prompt Server나 데이터베이스의 실제 가용성은 패키징 및 공개 계약 검증의 선행 조건이 아니며, 필요한 응답과 설정은 격리된 입력으로 대체할 수 있다.
- 운영 서버 배포, 컨테이너 이미지, 패키지 저장소 게시, 네트워크 부하 및 장기 성능 평가는 이번 1시간 범위에서 제외한다.
- 검증 실행 환경에는 각 배포 단위가 선언한 지원 런타임과 저장소 내용에 대한 읽기 권한이 준비되어 있다.
